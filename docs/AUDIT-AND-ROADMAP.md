# Miscord: ревью проекта и план улучшений

Документ описывает текущее состояние проекта, найденные проблемы и порядок их устранения.
Цель — привести приложение к состоянию «работает, синхронизировано между пользователями,
выглядит и ощущается как Discord».

Дата ревью: август 2026. Ревью охватывает бэкенд, фронтенд, инфраструктуру и документацию.

---

## Краткое резюме

Проект содержит много качественно сделанных отдельных частей: голосовые каналы на WebRTC,
демонстрация экрана, шумоподавление на AudioWorklet, работающая авторизация, деплой с SSL.
Проблема не в отсутствии функций, а в том, что части **не соединены между собой**.

Главный дефект: **текстовый чат не работает**. Не «работает плохо» — не работает совсем.
Пользователь пишет сообщение, нажимает Enter, поле очищается, и сообщение исчезает бесследно.
Оно не появляется на экране, не сохраняется в базу и не доходит до собеседника.

Причина — рассинхронизация внутри фронтенда. В приложении одновременно живут два независимых
хранилища данных, и в каждом есть своё поле «текущий пользователь»:

- `frontend/src/store/store.ts` — здесь пользователь заполняется при входе,
- `frontend/src/lib/store.ts` — здесь пользователь **всегда пустой**, потому что функция
  `setUser` определена, но нигде в коде не вызывается.

Компонент чата берёт пользователя из первого хранилища и считает, что всё в порядке,
а функция отправки живёт во втором хранилище и молча выходит, не найдя пользователя:

```ts
// frontend/src/lib/store.ts
sendMessage: (content: string) => {
  const { currentChannel, user } = get();
  if (currentChannel && user) {   // user здесь всегда null -> тело никогда не выполняется
    ...
  }
},
```

При этом на бэкенде чат реализован: есть WebSocket-эндпоинт `/ws/chat/{channel_id}`,
который принимает сообщения, сохраняет их в базу и рассылает остальным участникам.
Фронтенд к нему просто не подключается — во всём коде фронтенда нет ни одного упоминания
`ws/chat`. Работающий сервер и работающий клиент существуют, но между ними нет провода.

Остальные проблемы — того же рода: дублирование, недоделанные связи и накопившийся мусор.

## Часть 1. Что сломано (функциональные дефекты)

### 1.1. Текстовый чат не отправляет сообщения

Описано выше. Дополнительные детали:

- сообщения нигде не загружаются при открытии канала — истории переписки нет;
- REST-эндпоинта для получения истории сообщений на бэкенде **не существует**,
  сообщения можно только писать через WebSocket, но не прочитать после перезахода;
- у сообщений нет ни редактирования, ни удаления;
- бэкенд умеет рассылать событие «пользователь печатает» (`typing`), фронтенд его не слушает.

### 1.2. Сессия не восстанавливается после перезагрузки страницы

В `frontend/src/store/store.ts` в браузере сохраняется только токен:

```ts
{
  name: 'auth-storage',
  partialize: (state) => ({ token: state.token }),
}
```

Флаг `isAuthenticated` и объект пользователя не сохраняются, а запроса «кто я»
(`GET /api/auth/me`) при старте приложения нет. Главная страница проверяет
`if (!isAuthenticated || !token)` и отправляет на логин. Итог: пользователь с
действующим токеном при обновлении страницы выкидывается на форму входа.

### 1.3. При создании сервера каналы «выдумываются»

`frontend/src/components/ServerList.tsx` после создания сервера подставляет каналы
с фиксированными идентификаторами 1 и 2:

```ts
channels: [
  { id: 1, name: 'general', type: 'text', serverId: newServer.id },
  { id: 2, name: 'General', type: 'voice', serverId: newServer.id }
]
```

Настоящие идентификаторы, которые вернул сервер, игнорируются. Интерфейс показывает
каналы, которых в базе нет под такими номерами.

### 1.4. Список участников голосового канала ломается

Бэкенд в `GET /api/channels/voice/{id}/members` отдаёт поле `id`, а интерфейс в
`ChannelSidebar.tsx` читает `participant.user_id`. Для каналов, где пользователь
не находится в голосе, индикаторы демонстрации экрана и контекстное меню не работают.

### 1.5. События, которых никто не присылает

Фронтенд подписан на события, которые бэкенд никогда не отправляет:
`user_left_channel`, `channel_updated`, `participant_status_changed`, а также
`screen_share_started` / `screen_share_stopped` на канале уведомлений
(бэкенд шлёт их только в голосовой сокет). Код-обработчик есть, срабатывания нет.

### 1.6. Ответы API про сервер приходят в двух разных форматах

- `GET /api/channels/` (список) возвращает поля `text_channels` и `voice_channels`,
  причём **всегда пустыми**, хотя каналы при создании сервера создаются;
- `GET /api/channels/{id}` (детали) возвращает единый плоский список `channels`.

Кроме того, в списке серверов поле `owner` всегда подставляется как текущий пользователь,
а не реальный владелец, и `members_count` всегда равен нулю.

### 1.7. Redis подключён, но не работает

`connection_manager.py` публикует сообщения в канал Redis `text_channel:{id}`, а слушатель
написан под префикс `channel:` — и, что важнее, **функция-слушатель нигде не вызывается**.
Публикация в пустоту. Практическое следствие: приложение нельзя запустить более чем в одном
экземпляре, состояние соединений живёт только в памяти одного процесса.

Плюс адрес Redis захардкожен в коде (`redis://redis:6379`) вместо чтения из настроек.

## Часть 2. Почему выглядит несогласованно

### 2.1. Две UI-библиотеки в одном приложении

Одновременно используются:

- **Tailwind CSS + shadcn/ui** (Radix) — главный экран, список серверов, чат;
- **Material-UI v7** — страницы входа и регистрации, диалоги, аватары, меню в боковой панели.

У них разные шрифтовые размеры, тени, скругления, поведение при наведении и анимации.
Пользователь буквально видит два разных приложения: логин выглядит как Material-интерфейс
от Google, а основной экран — как Discord.

### 2.2. Цвета не соответствуют Discord и продублированы

Основной акцентный цвет Discord — blurple `#5865F2`. В теме проекта
(`frontend/src/app/globals.css`) задано `--primary: 235 86.1% 77.5%`, что даёт примерно
`#9BA4F5` — заметно бледнее и «водянистее» оригинала.

Одновременно в компонентах цвета прописаны вручную мимо темы:

```tsx
backgroundColor: 'rgb(88, 101, 242)',        // ChannelSidebar.tsx
backgroundColor: 'rgb(47, 49, 54)',          // ChannelSidebar.tsx
```

Зелёный «онлайн» встречается в трёх разных оттенках: `#43b581`, `#22c55e`, `#00ff88`.
Единого источника правды для цветов нет.

### 2.3. Отсутствуют элементы, которые делают Discord узнаваемым

Не реализованы: аватары (вместо них первая буква имени), статусы присутствия
(онлайн / отошёл / не беспокоить), индикатор «печатает», реакции на сообщения,
эмодзи, упоминания через `@`, группировка подряд идущих сообщений одного автора,
разделители дат, вложения и файлы, поиск, настройки профиля, роли и права, личные сообщения.

Пункты «исключить» и «заглушить» в контекстном меню присутствуют, но помечены `disabled`
с комментарием `TODO`.

## Часть 3. Почему в проекте тяжело разобраться

### 3.1. Фронтенд наполовину мигрировал с CRA на Next.js

Реально работает Next.js 14 (App Router). Но рядом лежат живые файлы от старого
Create React App, которые не участвуют в сборке и вводят в заблуждение:
`src/index.tsx`, `src/App.tsx`, `src/index.css`, `public/index.html`.

Ирония: именно в мёртвом `src/index.tsx` находится тема с **правильными** цветами Discord
(`#5865F2`, `#36393f`, `#2f3136`), которая никак не влияет на приложение.

### 3.2. Шесть хранилищ состояния, половина мертва

| Файл | Что содержит | Используется |
|---|---|---|
| `store/store.ts` → `useAuthStore` | авторизация | да |
| `store/store.ts` → `useStore` | пустая заглушка | нет |
| `lib/store.ts` → `useStore` | серверы, каналы, сообщения | да |
| `store/slices/voiceSlice.ts` | голос | да |
| `store/noiseSuppressionStore.ts` | шумоподавление | да |
| `store/channelStore.ts` | каналы (другая модель) | нет |
| `store/chatStore.ts` | сообщения (третья модель) | нет |
| `hooks/redux.ts` | только комментарии | нет |

Два разных хранилища называются одинаково — `useStore`. В мёртвых хранилищах
идентификаторы имеют тип `string`, в живых — `number`.

### 3.3. Компоненты-гиганты и мёртвые компоненты

`ChannelSidebar.tsx` — **1146 строк**, совмещает список каналов, подключение к голосу,
панель пользователя, обработку демонстрации экрана, контекстное меню с регулятором
громкости, диалог настроек шумоподавления и модальные окна создания каналов.

`ChatArea.tsx` — **773 строки**, из которых большая часть посвящена не чату, а
полноэкранному просмотру демонстрации экрана с ручными манипуляциями DOM.

`voiceService.ts` — **1621 строка** с примерно 164 вызовами `console.log`.

При этом не используются вовсе: `VoiceOverlay.tsx`, `UserPanel.tsx`,
`ScreenShareOverlay.tsx`, `ScreenShareToast.tsx`, `VoiceConnectionStatus.tsx`,
`ui/checkbox.tsx`. Функциональность из них скопирована внутрь гигантов.

### 3.4. Путаница в названиях: «канал» означает три разных вещи

| Discord | В коде бэкенда | Во фронтенде |
|---|---|---|
| Сервер (гильдия) | `Channel` | `Server` |
| Текстовый канал | `TextChannel` | `Channel` |
| Голосовой канал | `VoiceChannel` | `Channel` |

Слово `channel_id` в разных местах означает то сервер, то текстовый канал, то голосовой.
В адресе `/ws/chat/{channel_id}` это идентификатор комнаты, а внутри сообщения
передаётся другое поле — `text_channel_id`.

### 3.5. Мусор в корне репозитория

Девять `.md` файлов, из которых четыре — заметки о разовых происшествиях, а не документация:
`FIX-MIXED-CONTENT.md`, `ОПТИМИЗАЦИЯ-ЗАВЕРШЕНА.md`, `NEW-FRONTEND-DOCKER-READY.md`,
частично `QUICK-DEPLOY.md` (сокращённый пересказ `DEPLOY.md`).

Семь shell-скриптов, из которых три — одноразовые костыли под конкретный инцидент:
`commit-and-deploy.sh` и `fix-mixed-content-commit.sh` просто делают `git add . && git push`
с заранее написанным текстом коммита, `fix-ssl-path.sh` чинит путь к сертификату.

Также: пустой файл `t.txt`, корневой `package.json` с зависимостями, которые никем не
используются, и `package-lock.json` к нему на 19 КБ, второй файл `docker-compose.simple.yml`,
не упомянутый ни в одном документе.

### 3.6. README описывает несуществующий проект

README рассказывает про React 18 + Material-UI + Redux Toolkit, переменные `REACT_APP_*`,
запуск через `npm start` и доступность на `localhost:3000`. В действительности:
Next.js 14 + Tailwind + Zustand, переменные `NEXT_PUBLIC_*`, запуск `npm run dev`,
а порты 3000 и 8000 в `docker-compose.yml` наружу вообще не проброшены — вход только
через nginx на портах 80 и 443.

Новый разработчик, следуя README, не запустит проект.

## Часть 4. Безопасность

Проблемы перечислены по убыванию серьёзности.

1. **Секретный ключ по умолчанию прописан в коде.**
   `backend/app/core/config.py`: `SECRET_KEY: str = "your-secret-key-here-change-in-production"`.
   Это же значение продублировано в `docker-compose.yml`. Зная его, можно подделать токен
   любого пользователя. Пароль базы `miscord_password` также лежит в открытом виде в compose.

2. **Отладочные эндпоинты открыты всем без авторизации.**
   `/api/debug/websocket-stats`, `/api/debug/cleanup-connections`, `/api/debug/health`.
   Второй из них позволяет любому желающему сбрасывать соединения пользователей.

3. **WebSocket чата не проверяет права.**
   `websocket/chat.py` проверяет только валидность токена. Любой авторизованный пользователь
   может подключиться к любому каналу по номеру и писать туда сообщения, которые сохранятся
   в базу. Проверки членства в сервере нет.

4. **Голосовой WebSocket тоже не проверяет членство** — проверка удалена, о чём
   свидетельствует комментарий в `websocket/voice.py`.

5. **Токен живёт 7 дней, отозвать его нельзя.** Refresh-токенов нет, разлогинивание
   происходит только на стороне браузера, флаг `is_online` при выходе не сбрасывается.

6. **Токен хранится в двух местах** — в `localStorage` под ключом `access_token`
   и в хранилище Zustand. Разные части кода читают разные копии.

7. **Ограничения частоты запросов (rate limiting) нет.** Регистрацию, вход и отправку
   сообщений можно вызывать без ограничений; приглашение по имени пользователя позволяет
   перебором выяснить, кто зарегистрирован.

8. **`echo=True` у движка базы** — все SQL-запросы пишутся в логи.

## Часть 5. Инфраструктура

- **Миграций базы нет.** `alembic` указан в зависимостях, но папки с миграциями не существует.
  Таблицы создаются вызовом `Base.metadata.create_all` при старте, который **не умеет изменять
  уже существующие таблицы**. Любое изменение модели на работающем сервере потребует ручных
  действий с риском потери данных.

- **Бэкенд в «продакшене» запускается в режиме разработки:** в `docker-compose.yml` команда
  содержит `--reload`, а исходный код монтируется внутрь контейнера через volume.

- **Проверок готовности сервисов нет.** У postgres, redis и backend отсутствует `healthcheck`,
  а `depends_on` указан без `condition: service_healthy` — бэкенд может стартовать раньше базы.
  У фронтенда healthcheck использует `wget`, которого нет в образе `node:18-alpine`.

- **Контейнер бэкенда работает от root**, сборка не многоступенчатая (у фронтенда, наоборот,
  всё сделано правильно: три стадии и непривилегированный пользователь).

- **Ограничения памяти и CPU не заданы** ни одному сервису.

- **Nginx без SSL в репозитории.** В git лежит HTTP-версия конфига, HTTPS-версия применяется
  скриптом при деплое. Файл `nginx-initial.conf` полностью идентичен `nginx.conf`.
  Путь к сертификату захардкожен с суффиксом от прошлого инцидента: `miscord.ru-0001`.
  Gzip, кеширование статики и заголовки безопасности есть только в SSL-версии.

- **Домен `miscord.ru` захардкожен минимум в 15 файлах**, IP-адрес сервера — в документации
  и скриптах.

- **Нет CI/CD** (папка `.github` отсутствует), **нет тестов** ни на бэкенде, ни на фронтенде,
  **нет настроенных линтеров** (`.eslintrc` отсутствует, для Python нет ни ruff, ни black),
  нет pre-commit хуков.

- **`.gitignore` неполон**: не игнорируются `frontend/.next/`, `certbot/` (то есть сертификаты
  можно случайно закоммитить), `*.pyc`, файлы IDE.

## План улучшений

Этапы упорядочены по зависимостям: каждый следующий опирается на предыдущий.
Внутри этапа задачи можно выполнять параллельно.

### Этап 0. Закрыть дыры в безопасности

Делается первым, потому что не зависит ни от чего и устраняет реальный риск.

1. Убрать значения по умолчанию для `SECRET_KEY` и пароля базы из кода и compose;
   читать их только из переменных окружения, при отсутствии — падать с понятной ошибкой.
2. Закрыть `/api/debug/*` авторизацией администратора либо удалить.
3. Добавить проверку членства пользователя в сервере при подключении к чат-сокету
   и к голосовому сокету.
4. Отключить `echo=True` у движка базы.
5. Сгенерировать новый секретный ключ и сменить пароль базы на сервере.

### Этап 1. Починить чат — главная причина жалобы

Это работа, после которой приложение впервые станет действительно работать.

1. Убрать хранилище `lib/store.ts` как источник данных о пользователе, оставить один
   `useAuthStore`. Устранить дублирование поля `user`.
2. Подключить фронтенд к существующему `/ws/chat/{channel_id}`: отправка сообщения идёт
   в сокет, входящие сообщения попадают в состояние и на экран.
3. Добавить на бэкенд REST-эндпоинт истории сообщений с постраничной загрузкой
   (`GET /api/channels/text/{id}/messages?before=&limit=`) и индекс по `text_channel_id`
   в таблице сообщений.
4. Загружать историю при открытии канала, подгружать более старые сообщения при прокрутке вверх.
5. Добавить оптимистичную отправку: сообщение появляется сразу с пометкой «отправляется»
   и заменяется настоящим после подтверждения сервера, при ошибке — помечается неудачным
   с возможностью повторить.
6. Подключить индикатор «печатает» — событие на бэкенде уже есть.
7. Восстанавливать сессию при загрузке страницы через `GET /api/auth/me`, чтобы обновление
   страницы не выкидывало на логин.

### Этап 2. Синхронизировать контракты между фронтендом и бэкендом

1. Привести `GET /api/channels/` и `GET /api/channels/{id}` к единому формату ответа,
   заполнять реальные `text_channels` / `voice_channels`, настоящего владельца
   и настоящее число участников.
2. Исправить `ServerList.tsx`: использовать идентификаторы каналов, пришедшие с сервера,
   вместо жёстко прописанных 1 и 2.
3. Привести поле участника голосового канала к единому имени (`user_id`) на обеих сторонах.
4. Либо реализовать на бэкенде события `user_left_channel`, `channel_updated`,
   `participant_status_changed`, либо убрать их обработчики с фронтенда.
5. Пересылать события демонстрации экрана в сокет уведомлений, раз фронтенд их там ждёт.

## Рекомендуемый порядок работы

Первым делом — этапы 0 и 1. Они устраняют то, из-за чего приложением нельзя пользоваться
и из-за чего его небезопасно держать в интернете. После этапа 1 чат заработает и появится
синхронизация между пользователями.

Затем этапы 2 и 3: контракты и чистка. Без них любая новая функция будет добавлять путаницы,
потому что придётся угадывать, какое из двух хранилищ и какой из двух форматов ответа верен.

Этап 4 даёт видимый результат — приложение начнёт выглядеть как единый продукт.
Этапы 5–7 расширяют функциональность и приводят в порядок эксплуатацию.
